# Rules definitions

The game rules are data, in `definitions/`.
This page is for developers and rules curators.
It explains how the app reads the rules files and applies them.

The JSON says **what** the rules are; the rule engine (`internal/core`) decides **how** to apply them.
Most special rules only matter during matches, which are played away from the app, so the app displays them next to the unit, item or company they affect.
A few rules change the campaign, and the engine applies them: injury rolls, progression, Influence and the Break Point.

## Editing the Battle Companies file

Edit the file, then check it in this order:

1. Run `make check-ruleset FILE=...`.
   It runs the Go validator alone, on any file.
2. Run `make validate` (`tools/validate_definitions.py`).
   It runs the Go validator on the shipped file, together with:
   - the JSON Schemas;
   - the curator's extra checks (`tools/lean_checks.py`: company texts, aura radii against the texts, rule-target keywords, Tabletop Simulator models);
   - the glossary and the concept graph.

   It must report 0 errors.
3. Run `make concept-graph` when the file, the vanilla file or the glossary changed.
   The concept graph records their hashes.
4. Run `make test`.
   It runs the Go tests and the Python tests of `tools/`.
   The golden snapshots (`internal/core/testdata`) show every change to what the app derives from the file (armoury, auras, Tabletop Simulator lists, audit).
   Review a change that moves a golden, then regenerate it as [testing.md](testing.md) says.

## Dependency direction and resolution order

References only point one way: **Battle Companies to vanilla and glossary**.
Glossary terms may point to other glossary terms (`see`).
Vanilla and the glossary never refer to the Battle Companies file.

A name the Battle Companies file does not define is looked up in vanilla, then in the glossary.
The order is:

1. A definition embedded in the entity that uses it.
2. The Battle Companies file.
3. Vanilla.

Battle Companies wins.
A rule with a vanilla name is its generalisation ("this Hero" for a named character) and carries `overrides`.
Vanilla scenarios and army bonuses are not used.
Units are never redefined: a company's unit is a vanilla unit plus what the company changes.

A vanilla name defined twice is resolved by the loader to the **first occurrence**.
`vanilla.pins` in the Battle Companies file names the few where another occurrence wins.
A pin is `{kind, name, occurrence}`; occurrences count the heroes list before the warriors list, case-insensitively.
A pin whose occurrence does not exist is a warning ("vanilla drift").
The reviewed list and its notes are in `tools/data/duplicate_decisions.json`.

## The header and the identity of a ruleset

Every file the project authors (Battle Companies, glossary) starts with a top-level `name` and `version`, both strings.
The Battle Companies ones come from the rulebook's title page ("Stable Released Version 1.1" is `1.1`).
The vanilla file is a third-party store, so it keeps `game` and `appVersion`.

`core.RulesetMeta` reads these fields, and the marker that tells the kind of file:

- `extends` for Battle Companies;
- `terms` for the glossary;
- `appVersion` for vanilla.

A ruleset is identified by the content hash of its three files: the SHA-256 of the compacted JSON, so whitespace does not matter.
Any change to any field is a new ruleset.

## The loader

`core.LoadRuleSet(vanilla, bc, glossary, log)` (`internal/core/audit.go`, `ruleset_v2.go`) merges the three files into the in-memory maps the engine queries:

1. Parse the vanilla file (`ParseVanillaWith`) and build the glossary (`BuildGlossary`).
2. Refuse a Battle Companies file of the old format (no `schemaVersion`, or 1) with the one issue that says so.
3. `lean.Decode`: the strict binder, `extends` and defaults, name resolution against the file, vanilla and the glossary, validation. Any error comes back as one `*RulesetReport`.
4. Re-parse vanilla with the duplicates the document pins (`LeanPins`) and apply its fill-ins (`ApplyLeanFillIns`: race, faction and unit type that vanilla leaves empty for a unit or mount).
5. `LeanBook` builds the whole rule set from the typed document; `LeanGlossaryExtras` adds the glossary terms the file implies (one per item, class rules, creatures, wanderers, consumables).

`RuleSet.Doc` carries the document. The readers, each in `internal/core`:

| Reader | Reads |
|---|---|
| `companies_lean.go` (`LeanCompanies`) | Company pages and profiles: charts, starting force, promotions, hero upgrades, own units (aliases), limits, officers, notes, oath |
| `gear_lean.go` | The armoury, annotations, item classes, abilities, creatures, wanderers, limits, fill-ins, unsold options |
| `paths_lean.go` | Paths: progression rows, limits, the path offers, starting actions and powers, characteristic limits |
| `rules_lean.go` | Rule texts, labels, targets (`LeanRuleTargets`), the aura table (`LeanAuraTable`), casting (`LeanCasting`) |
| `scenarios_lean.go` | Scenarios, scoring objectives, rewards, the selection tables |
| `campaign_lean.go`, `companyrules.go`, `recruitrules.go`, `aftermath.go`, `live_break.go` | The `campaign` parameters (below) |
| `tts_lean.go` | Tabletop Simulator figures ([tabletop-simulator.md](tabletop-simulator.md)) |
| `glossary_lean.go` | Glossary terms from the file |

**Maps, not database lookups.**
The files are parsed once into immutable maps keyed by name, read concurrently without locks.

**Shared by content.**
Campaigns with the same three hashes share one set of maps.
The cache is keyed by that triple and builds each set once, even under concurrent requests.
The concept graph is computed into adjacency maps on first use per triple (`core.Concepts`).

**Uploaded rulesets** are stored once per hash, content-addressed, in the database.
A campaign only references the hashes.
The shipped files go through the same path.

## Normalisation: `extends`, defaults, names

`lean.Normalise` runs once after binding and is idempotent.

**`extends`** applies to companies, units, items and paths.
A child gets the base's value for every field it leaves at the zero value.

- These fields stay the child's own: name, id, aka, definition, note and `tts` for items; faction, description, epigraph, notes and specialRules for companies.
- A list or an object the child writes replaces the base's as a whole.
- A child cannot override `true` with `false`.
- A loop of bases is an error.

**Defaults** it fills:

- `id`: the slug of the name.
- A gear `gold`: the rating.
- A company's `faction` (its name) and `maxModels` (`campaign.company.maxModels`).
- `ownPath.path`: "On Their Own Path".
- A path's `kind` (`heroic`) and `dice` (`campaign.progression.hero.roll`).
- A scenario's and a scoring objective's `side` (`both`).
- A rule target's `appliesTo` (`own`) and `match` (`any`).
- Chart and start `count` (1).

**Names** compare with one function, `lean.NameKey` / `core.NameKey` (`internal/core/names.go`).
It lower-cases, drops accents and apostrophes, and turns every other run of punctuation or spaces into one space.
So `Lothlorien` is `Lothlórien` and `Lake-Town` is `Lake Town`.
Plurals and "made" are not folded.

Where the engine resolves a name:

| Name | Where | Rule |
|---|---|---|
| a name against another, or a map key | `sameName`, `NameKey` | `NameKey`; `aka` lists true synonyms; an `aka` that is a vanilla name of something else is refused |
| a company's own name for a unit | `CompanyProfile.AliasFor` | the company's own `units[]` entries with `extends` (label unique); a top-level `units[]` entry with `extends` is accepted by the checker but not read as an alias |
| the vanilla profile of a unit name | `RuleSet.ResolveUnit` | the company's own units (a unit on another, or a brand-new one), then the shared top-level `units[]`, then vanilla; a brand-new unit (`profile`, no `extends`) is registered as a vanilla-shaped profile when the book is built (`RegisterLeanUnits`) |
| a company by name | `BCBook.Company` | exact, else folded; `aka` |
| an item name against an item | `ItemKey`, `namesItem`, `SameItem` | gear identity only: plural s, "made", `&`, case, punctuation; the vanilla file's spellings need a bridge, the Battle Companies file writes exact names or `aka` |
| keyword spellings of the vanilla file | `keywordSpellings` | a fixed table in the vanilla bridge (the vanilla file is read-only) |

Two rule-name pairs that `NameKey` would conflate stay apart by distinct names or `overrides`:

- `Rapid Fire (Bolt Thrower)` and `Rapid-fire Bolt Thrower`;
- the vanilla `Swap with Me` and the Battle Companies `Swap with Me!`.

A rule written with its argument (`Terror (Beast)`, `Poisoned Attacks (X)`) resolves to the rule of its base name (`lean.BaseRuleName`).

## Derived, not stored

The app computes the following from the data.
The file does not carry them and does not need to.

- **Path offers and texts.**
  - The path picker's summary and offers (`DerivePathOffers`) come from the table, `heroicAction`, `spells`, `mastery` and `signature`.
  - The text of a row that grants one rule is `RuleRowText` (`Name (Tag) - definition`).
  - The text of a row that only improves characteristics is `StatRowText`.
  - `hidden` comes from the kind.
  - A row keeps its `text` only where the words cannot be derived: a rule vanilla words otherwise, a mastery row with its "OR improve ..." alternative, a result with a ceiling or a second roll.
- **Item classes.**
  - They come from the vanilla type (`ClassesOfVanillaType`): mount, bow, armour, shield, banner, throwingWeapon, blowpipe, horn, spear, two-handed, upgrade.
  - `gold` comes from the rating.
  - `grantedTo: mount` comes from a mount that grants rules.
  - A mount's stat block, `restrictions` (badges) from `who`, and `pricedAs` items sold at their base's price are derived too.
- **Reserved options.**
  - The options of vanilla units whose `availableIn` names only heroes (Lorien Guard, Hearthguard, Helmingas...) are never offered by a Choice of Options (`VanillaBook.ReservedOptions`).
  - A company reaches one explicitly through a unit's `with`.
  - The profile wargear no armoury sells (armour and hand weapons, natural weapons) is derived too (`ProfileWargearNotSold`).
    A model always starts with it; it is never an option or buyable.
- **Other derived values.** Ids; the keywords of a unit (`core.UnitKeywords`, [unit-keywords.md](unit-keywords.md)); the company rules sentence of `elvenWeaponry` (`ElvenWeaponrySentence`); the hero-upgrade rule text; the effective stats of a unit (see below).

## Engine parameters

Every value the engine uses is a field of `lean.Campaign` (`campaign.go`) or of a few other sections.
Each is **required with a range**; the code has no default.
A missing or out-of-range value is a load error that names the path, in the upload report and at start-up.

`lean.ParameterIDs` maps the ids of the engine parameters (A1, B3, C1...) to their paths.
The values, ranges and meaning of each are in the [guide](customizing-rulesets.md#11-engine-parameters).

Where the engine reads them:

| Parameters | Reader |
|---|---|
| `campaign.company` (maxModels, leaders, sergeants, heroStart, equipmentSlots), `limits[]`, creature and wanderer counts, `paths[].limit` | `ParseCompanyRules` (`companyrules.go`) → `BCBook.Shape()`, `CompanyProfile.Leaders/Sergeants/HeroStart`, `CompanyUnit.BaseSlots`, the limit rules; a company's own `maxModels` must hold the officers |
| `campaign.recruitment` (die, adjust, rare), `campaign.company.startingInfluence`, `aftermathEffects[rendezvous\|vantagePoint].range` | `ParseRecruitRules` (`recruitrules.go`) → `BCBook.Recruiting()`; every chart is checked to cover `1..sides` once; the recruit window prints them (`RecruitInfo.Rules`) |
| `campaign.progression`, `campaign.experience`, `campaign.influence`, `campaign.injuries` | `ParseProgression`, `AftermathRules` (`aftermath.go`: `LevelEvery`, `Gains`, injury dice and rows, `NoPromotionBy`); `BCBook.ExperienceGain(key)` |
| `campaign.breakPoint` (default percent, comparison, courage test dice and `passIf`, `scenarioExceptions[]`), a company's `breakPoint` (a share: `"1/2"`, or a percent number; always a whole percent) | `BreakRules` (`live_break.go`) → `BreakConfig` for the live fold; the test is `casualties * 100` against `percent * startingModels` (never rounded) |
| `campaign.rating` | `LeanRating`: `RatingRules.Wargear` (the hero rating threshold), `PerPoint` (`rating.hero.perPoint`), `PerSpecialRule`, `PerMinorSpecialRule`, `MaxMinorSpecialRule`; `BCBook.HeroBonus` is the profile bonus of a new hero |
| `campaign.scenarioSelection` | `LeanScenarios`; the ranges partition `1..sides` and each table lists `sides` scenarios |
| `campaign.characteristicLimits` | `LeanProgression`: `lowerIsBetter`, `peak` (and `willMaxOverrides`), `average`, `increases.courageIntelligenceTotalCap {value, includesGear}` |
| `magic.floor`, `magic.maxPerPower`, `magic.powers` | `LeanCasting` |
| `gear[].grantsSlots` | `Equipment.GrantsSlots`; `CompanyUnit.Slots()` adds them to `BaseSlots` (there is no Backpack name check) |

**Dice are data.**
Every dice string is an `[N]dM` spec: N from 1 to 10, M from 2 to 100, and `d66` is refused.
It is parsed once at load with `lean.ParseDice` (`core.DiceSpec`; `core.ParseDiceAt` names the key in the error) and rolled with `core.Dice.Roll(spec)`.
A table that does not cover the dice of its key is a load error naming the path (`core.CheckCovers`).

**Typed tables.**
These `campaign` sections are typed.

- `campaign.injuries` (`lean.Injuries`, `campaign_injuries.go`):
  - the rows with their `effects` (a closed vocabulary), persistence and `retireAtCount`;
  - `disables`, `grantsAtCount`, `heals`, the dice grants, and the `treatment` methods with their rolls.
  - The upload checks the ranges, the vocabularies and the cross references, with the path of the key.
    It refuses a treatment target the dice cannot reach, a `healable` or `heals` key that is no hero injury, and a `disables` entry without its classes, names or ability.
  - `core.LeanInjuries` and `core.LeanAftermath` read the typed values.
- `campaign.againstTheOdds` (`lean.AgainstTheOdds`, `campaign_ato.go`):
  - the bonuses (key, name, rating, `appliesIn`, `gains`, `count`, the structured `grants`, `kits` and `purchase`), the budget and the eligibility;
  - bonus keys and kit names are unique;
  - `core.LeanATO` and `core.LeanAftermath` read the typed values.
- `campaign.breakPoint`: `scenarioExceptions[]` names a scenario of `scenarios[]`, spelled as the scenario is, or a scenario setting. It has a text or an effect, and a who.
- `campaign.aftermathEffects[]` (`lean.AftermathEffect`, `campaign_aftermath.go`):
  - `kind` is a closed vocabulary and `key` is unique;
  - a replacement names an injury result of the charts;
  - a `scenario` names a scenario of `scenarios[]`.
- `campaign.progression`, `campaign.scenarioSelection` and the hero and warrior progressions list every key they accept.
  A key that is not in the reference is an error.
  No open `Rest` objects are left in the campaign.
- `campaign.characteristicLimits` (`lean.CharacteristicLimits`, `campaign_limits.go`):
  - `lowerIsBetter`, `average` and `peak` with one `{max, best, maxIncrease}` per characteristic;
  - `willMaxOverrides`, where each key is a path of `paths[]` and the value is 1 to 10;
  - the cap on Courage and Intelligence.
  - A path's `maximums` has the same `{max, best, maxIncrease}` shape and is typed with it.
  - A key that is not a characteristic is an error.
- `campaign.rating.hero`: `perPoint` lists each characteristic once; the per-rule numbers are ranged and 0 when absent.
- `campaign.options[]` (`lean.CampaignOption`) is the single list of switches.
  - Fields: `key`, `scope` (`rules` or `app`), `label`, `description`, `default`, `implemented`, `swaps`.
  - The app switches the keys it knows and lists any other as unsupported, with a warning in the log.
  - `core.ParseCampaignOptions` binds the stored file to the lean model.
- `campaign.company.oaths`: `good` and `evil`, each `{vow, text}`. `leanOath` reads it.
- `campaign.matchInput` describes what the players enter: `perCompany[]`, `perModel[]`, `result`, `aftermath.order`.
  The app builds its match forms from its own tables and does not read it.
  So the `default` and `options` of a field stay open values: a flag, a number or a word; a list or the path of a table.

**Open values.**
Two campaign values are genuinely open:

- `campaign.gold`: any JSON describing where Gold comes from. Gold itself is a number on the company.
- `campaign.influence.spend`: prose and data about what Influence buys.

The app reads neither.
The schema accepts anything there, and the reference says so.

Everything else under `campaign` lists every key it accepts, with its vocabulary and range, and an unknown key is an upload error.
Objects that record a house-rule decision carry `confirmedByUser` and `defaultNotConfirmed` lists.

## How the engine applies what it reads

These behaviours are worth knowing when you change the data.
Tests cover each one; the code is the truth.

Contents: [Items and prices](#items-and-prices) | [Stats and poison](#stats-and-poison) | [Limits](#limits-and-who) | [Company structure](#company-structure) | [Scenarios, auras and Tabletop Simulator](#scenarios-auras-and-tabletop-simulator)

### Items and prices

- **Item identity** is the name.
  - `ItemKey` folds case, punctuation, the plural s and "made".
  - The same stats, class or price never make two items one.
  - A wargear price group is one item per name with the price repeated.
  - Chips and tooltips look the item up by its own name.
- **Who may buy what.**
  - A warrior may buy an item only when it is exactly one of the items its profile options name (`OptionItems`, `GearMatchesOption`).
  - A hero may buy any item of its company's profiles.
- **Bundles.**
  A start, chart or promotion row that names one piece of a multi-item profile option ("Shield and Spear") gives the unit the whole option.
  It prices the unit at the option's points (`completeBundle`).
- **Price rule.**
  A unit's points are the vanilla base profile cost plus the options it bought.
  Only wargear no option has is charged its armoury rating (`OptionsCover`).
  The audit flag `price-mismatch` checks every row.
### Stats and poison

- **Effective stats** (`applyGearStats`, `gearstats.go`):
  - armour by stage (best only);
  - the best active shield `defenceBonus`, cancelled by a bow, crossbow, two-handed weapon or pike unless a rule lifts it (Expert Rider while mounted, Phalanx);
  - the plain `modifiesStats` of unit upgrades.
  - Disabled (injured) gear gives nothing.
  - A shield's loss through the unit's own gear is a loadout condition and is computed.
- **Conditional bonuses are item text, never added to the stats.**
  A `defenceBonus` or `attacksBonus` flagged `conditional` (Pavise, Small Shield, Elven Glaive) is a note.
  So is a `statChanges[].condition`.
- **Poison** is the special rule `Poisoned Attacks (<weapon>)` of a unit.
  - Wargear stays plain, except the Blowpipe, which grants it.
  - *Envenom Weapon (X)* (`grantsForChosenWeapon`) is equipment bought with a chosen weapon of the unit's `PoisonableWeapons` (classes in `weaponClasses`).
  - The choice is final and belongs to the weapon's name.
  - `BuyEquipmentFor` refuses a purchase without a valid weapon.
### Limits and who

- **Limits.** Every limit is read from `limits[]`: `id`, `classes` or a keyword, `share`, `roundUp`.
  - `share` is an integer fraction such as `"1/3"`, or the older `maximumPercentage`.
  - A limit counts the model being recruited in the numerator and the denominator.
  - A company's keyword limit always rounds up.
  - The count is `LimitMax(share, n, roundUp)` with whole numbers only (`lean.Share`: `(n*num + den - 1)/den` rounding up, `n*num/den` rounding down).
  - A percent is converted to the exact fraction over 100 when the file is read.
    The check warns when a percent is nearly a simple fraction (see "Shares" in [customizing-rulesets.md](customizing-rulesets.md#shares-fractions-not-percentages)).
  - A company's `limits.exempt` takes a unit or item out of both the count and the base.
  - A model counts as Cavalry when its profile says so or it carries a mount.
- **Who** (`lean.Who.Admits`, the only reader) decides who may:
  - buy an item;
  - take a hero upgrade;
  - receive a granted rule;
  - be a starting hero;
  - wear Elven-made weaponry.

  The refusal it returns is the text the armoury shows.
### Company structure

- **Officers.**
  - A company has at most `leaders` Leaders and `sergeants` Sergeants; the rest are Heroes in the Making.
  - After the battle, a Sergeant replaces a lost Leader, then another Hero.
  - A Warrior is promoted to Hero only when no Hero is available (most Experience, ties by Rating then the controlling player).
    It gains Might, Will and Fate.
  - A Hero promoted to fill a place stays a Hero.
  - The Shire's Ranger replacement is the one case that displaces an officer ([frontend-company-building.md](frontend-company-building.md#ranger-of-the-north-replacement-shire)).
  - A unit On Its Own Path is never an officer.
- **Starting company** adds up to 105: 60 points of rating and gold, plus 5 each for Might, Will and Fate of 3 heroes.
  - The checker does not test it; `TestStartingCompanyPointsPlusGoldAre105InEveryCompany` does.
  - The documented exception is Defenders of the North (106: the book's list is 61 points at the current MESBG points).
  - A start unit that is a hero by its profile must be one of the officers (`ValidateStart`).
- **Promotions.**
  - The company's promotion applies only to the level-up roll.
  - An officer chosen at creation, a Warrior taking a lost officer's place and a recruit that joins as a Hero (`heroes.recruitAsHero`) keep their profile.
    Each gains the Might, Will and Fate point.
  - A unit the file marks `heroInTheMaking` starts as a Hero with its path to choose.
  - A warrior promoting to another unit keeps only the gear the new profile lists.
- **Rare N.**
  - At most N of the unit may be in the roster (`campaign.recruitment.rare`).
  - Injured units count; dead and promoted ones do not.
  - A rare-exhausted result is recruited as a lower one.
  - A lower result is a free choice of any lower result.
    It is allowed only when the rolled one cannot be recruited or a company rule says so (code, not data).
- **Paths.**
  - `endOfPath` ("On Their Own Path") is assigned automatically to the units a company's `ownPath` names.
  - With the option `customOnTheirOwnPath`, those units start as Warriors and take the homebrew path on a roll of 6.
  - Company Hero Upgrades may replace any rolled level-up result the hero does not already have.
- **Oaths.**
  - A company's `oath.text` holds `{name}` exactly once, never at the start or end.
  - `vow` is a button label of 1 to 40 characters.
  - `campaign.company.oaths.{good,evil}` have the same shape and serve companies of a custom file that have none.
### Scenarios, auras and Tabletop Simulator

- **Scenarios.**
  - A company's Victory Points are the sum of its objectives (`side` restricts to a role).
  - The most points wins; equal is a draw.
  - Rewards point at `campaign.aftermathEffects` entries, applied when their `condition` holds.
  - `campaign.matchInput` describes what the players enter per match.
- **Auras and targets.**
  - Rings are matched to units by item, rule, power, Heroic Action or `hero`, and merged per figure, kind, radius and tier.
    [aura-ranges.md](aura-ranges.md) is the spec.
  - Rule targets (`target`, `bareTarget`) feed the unit cards' "Works against / Works for" ([unit-keywords.md](unit-keywords.md)).
  - The curator's aura audit (what names a distance but draws no ring, and why) is `tools/data/aura_audit.json`.
- **Tabletop Simulator.**
  - `unit.tts` and `gear.tts` are the fixed mappings to the mod's model names.
  - The Go validator checks the shape.
  - When the gitignored `sources/tts/models.json` exists, `tools/lean_checks.tts_errors` checks every model against the mod's catalogue.

## The schema of the lean format

`definitions/battle_companies/battle_companies.schema.json` describes the lean file (JSON Schema 2020-12, with `$defs` per model struct).
The tools, the editors and the generated reference use it.
It is not used to check an upload: the decoder is the authority.

**The Go model is the contract and the schema is generated from it.**

- `internal/core/lean/model.go` and `campaign.go` carry the keys, types and tags (`required`, `enum`, `min`/`max`, `emin`/`emax`, `rest`).
- `schema_docs_test.go` carries the description of every object and key.
- `schema_gen_test.go` turns them into the schema by reflection.
- The generator writes once what a tag cannot say:
  - the polymorphic values (`Roll`, `DiceSpec`, `Rating`, `RuleRef`, `AdvanceTo`, `Scalar`, next to their `BindJSON` in `types.go`);
  - the `default` of each constant the defaults pass applies;
  - `schemaVersion` as `const 2`.

After changing the model or a description, run:

```bash
go test ./internal/core/lean -run TestSchemaUpToDate -update-schema    # rewrites the schema file
make ruleset-reference                                                 # then rewrites docs/customizing-rulesets-reference.md from it
```

The tests fail when the pieces disagree:

- `TestSchemaUpToDate`: the committed file is byte-for-byte what the model generates.
- `TestSchemaMatchesModel`: a second, independent reading against the struct tags.
- `TestSchemaDefaults`: each schema default is what `Normalise` writes.
- `TestSchemaFieldsAreDescribed`: every object and key has a description.
- `TestFixturesAgainstSchema`: every `testdata/valid/*.json` validates; for every invalid fixture the schema rejects, the decoder reports something at that path or beneath it.
- `tools/test_ruleset_reference.py`: the committed reference is what the generator makes.

The schema is slightly stricter than the binder in two places:

- A `null` on an optional key is accepted only where the model has a pointer to a scalar (`heroicAction`, `who.hero`).
- A dice spec with leading zeros (`02d6`) is refused.

`tools/validate_definitions.py` checks that the schema is valid and accepts the Go valid fixtures.

## Upload validation

An upload is validated as a whole before anything is stored.
Uploads come from the admin Rules files page and from the campaign form's file pickers.
Every problem is collected and returned; none stops the report early.

1. **Common checks.**
   `core.Rulesets.StoreAs`, `StoreAllAs` and `Check` run the same checks:
   - kind;
   - size (16 MB);
   - the announced hash;
   - well-formed JSON (a syntax error names its line and column);
   - shape limits (1,000,000 values, 64 levels);
   - the kind of document (`RulesetMeta`).
2. **The Battle Companies file** goes through the lean decoder (`lean.Decode`).
   - It is checked against the vanilla file and glossary uploaded with it in the same request (the campaign form's picks, `CheckSet`, the online validator).
   - What is not uploaded is the default (shipped) one.
     A single-file upload (the admin page, the form with only that file) uses the defaults.
   - A vanilla file or glossary that cannot be read is reported itself.
     The Battle Companies file is then checked against the shipped one, with a warning.
   - A file of the old format is refused with the one issue `schemaVersion 1 is not supported: ...`.
   - Vanilla and glossary files are checked against their JSON schemas.
3. **Any error** comes back as one `*core.RulesetReport` (wraps `ErrInvalidRuleset`).
   - `Issues()` gives `RulesetIssue{File, Path, Message, Hint, Closest, Warn}`.
   - `Truncated()` gives the count beyond 1,000.
   - Nothing is stored and no campaign is created.
   - `StoreAllAs` checks every uploaded file before inserting any.
4. **The dry run** is `CheckSet` (`Check` is its one-file form).
   - It sits behind the admin page's **Check this file** and the online validator at `/tools/validate` ([frontend-campaigns.md](frontend-campaigns.md#online-validator)).
   - It takes the three contents (nil: not given), returns one report with the issues grouped by file (vanilla, glossary, Battle Companies) and never writes.
   - At start-up the shipped Battle Companies file is checked against the shipped vanilla file and glossary, which are registered first (`RegisterDefaults`).

### The report format

Each issue is one report line: `<file>: <json path>: <message>`.
Two parts can follow:

- `; closest: "<name>"` when a name did not resolve.
- `  hint: <one line>` on the next line.

A warning starts with `warn: ` and does not block.
The order is the order of discovery and is deterministic.

The catalogue of messages is executable: `internal/core/lean/testdata/invalid/*.json`, with the wording pinned in `*.want` ([testing.md](testing.md)).

`make check-ruleset FILE=... [VANILLA=... GLOSSARY=...]` prints the report.
It exits 1 on errors and 2 when it could not run.

## The golden snapshot

`go test ./internal/core -run Snapshot` compares everything the app derives from the Battle Companies file with `internal/core/testdata/snapshot/`.
That covers all 37 companies: charts, armoury, profiles, progression, campaign tables and glossary extras.
`auras_golden.txt` and `tts_golden.txt` do the same for the aura rings and the Tabletop Simulator lists.

A golden that changes in a refactor means the refactor changed behaviour.
A deliberate data or engine change updates it (`-update-snapshot`, `-update-auras`) after the diff is reviewed ([testing.md](testing.md)).

`TestCustomRuleset*` rows change one engine parameter in a copy of the shipped file and check the effect through the built `RuleSet`, so nothing stays hard-coded.
`cmd/rulecheck/examples_test.go` runs the guide's examples.

## Audit report

`make audit` (`go run ./cmd/server audit [--out DIR]`) loads the shipped rules and writes one markdown file per Battle Company plus `index.md`.
The default output folder is `tmp/audit/` (gitignored), and no database is needed.

The data comes from the real code:

- `BuildDetail` and the recruit charts;
- `BCBook.Armoury`, and the armoury's `whyNot` for a warrior and a hero of every distinct profile;
- `GearMatchesOption`;
- the tooltip text `equipmentFor` shows.

The output is stable, so two runs can be diffed (`internal/core/audit.go`, `audit_render.go`).

The index counts anomalies per kind and company:

- `offer-not-derivable`, `option-unbuyable`, `option-unknown-item`
- `price-missing`, `price-mismatch`
- `unit-unresolved`, `unit-no-wargear`
- `duplicate-name`, `name-format`
- `tooltip-name`, `tooltip-missing`
- `rule-unresolved`, `partial-bundle`

Flags are leads for a reviewer, not verdicts.

## Reference tables (`reference` in the glossary file)

Besides `terms`, the glossary file carries structured rulebook tables that the terms only describe.
They are in `tools/glossary_reference.py` (hand-transcribed), and the validator and `tools/test_to_wound.py` check them.

`reference.toWound` is the To Wound Chart (rulebook page 44):

- `strengths` and `defences` run 1 to 10.
- `cells[s-1][d-1]` is the roll for Strength `s` against Defence `d`: `3+` to `6+`, `6+/4+`, `6+/5+`, `6+/6+` or `-`.
- `notation` and `notes` explain the cells.

The validator requires the complete grid, only those values, and monotonicity: never easier as Defence rises, never harder as Strength rises.

## The concept graph file

`definitions/concepts/concept_graph.json` (schema `concept_graph.schema.json`) is built by `tools/build_concept_graph.py` from the shipped triple.
It holds only what cannot be recomputed from the text:

- `builtFrom`: the three ruleset hashes, as `core.RulesetHash` computes them.
- `nodes`: the glossary terms exactly as the app builds them, via `go run ./tools/conceptnodes`.
- `edges`: `grants`, `cancels`, `lifts`, `requires`, with `via`.
- `ambiguous`.

Edges are derived from the lean file (item `grants`, path heroic actions and rule rows, shield `defenceBonus` cancellations and lifts, `requiresMount`, `who`) plus the reviewed `tools/concepts_curated.json`.

`make validate` fails on a stale graph; `make concept-graph` rebuilds and validates.
Design and consumers: [concept-graph.md](concept-graph.md).
Details of the checks: [tools/README.md](../tools/README.md).
