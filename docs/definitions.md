# Rules definitions

The game rules are data, in `definitions/`. The JSON says **what** the rules are; the rule engine (`internal/core`) decides **how** to apply them. Most special
rules only matter during matches, which are played away from the app, so the app mostly displays them next to the unit, item or company they affect; a few
(injury rolls, progression, Influence, the Break Point) change the campaign and are applied by the engine.

This page is the **engine side**: how the app reads the files and applies them. To write or change a ruleset use the authoring pages:

| Page | For |
|---|---|
| [customizing-rulesets.md](customizing-rulesets.md) | The tutorial: the file, names, units, items, paths, companies, scenarios, engine parameters, the validation loop, upload; a worked example per concept; a section for coding agents |
| [customizing-rulesets-reference.md](customizing-rulesets-reference.md) | Every key with type, default, allowed values and meaning (generated from the schema by `make ruleset-reference`) |
| [examples/customizing-rulesets](../examples/customizing-rulesets/README.md) | The tested example files the tutorial quotes |
| [../tools/README.md](../tools/README.md) | The commands: check, validate, glossary, concept graph |

| File | Role |
|---|---|
| `vanilla/data2024.json` | The base game: units, wargear, special rules (keywords), magical powers. A **reference store written by a third party, never edited** |
| `battle_companies/battle_companies.json` | Everything specific to Battle Companies 2nd CE, in the lean format (`schemaVersion` 2). **Hand-maintained**: the source of truth for the rule engine. Its schema is `battle_companies.schema.json`, generated from the Go model |
| `glossary/mesbg_glossary.json` | Concepts of the MESBG rules manual that the vanilla file leaves out (Heroic Actions, Stand Fast, the turn phases...), from the 2024 rules manual. Generated by `tools/build_glossary.py` |
| `battle_companies/reference/*.json` | Rulebook prose that no code reads (influence, gold, designer notes). **Never loaded** by the app and never uploaded |
| `concepts/concept_graph.json` | The reviewed edges between concepts (`grants`, `cancels`, `lifts`, `requires`) of the three files above, for the helper popups. **Generated** by `tools/build_concept_graph.py`; see [concept-graph.md](concept-graph.md) |
| `tools/data/*.json` | Records of curator decisions (reviewed vanilla duplicates, aura audit, Tabletop Simulator provenance), read by no code |

The rulebook, the Battle Companies document and anything converted from them are copyrighted: they stay in the gitignored `sources/`; the JSON files may be committed.

## Editing the Battle Companies file

Edit the file, then check it:

1. `make check-ruleset FILE=...` runs the Go validator alone, on any file. `make validate` (`tools/validate_definitions.py`) runs it on the shipped file together with the
   JSON Schemas, the curator's extra checks (`tools/lean_checks.py`: company texts, aura radii against the texts, rule-target keywords, Tabletop Simulator models), the glossary and the
   concept graph. It must report 0 errors.
2. `make concept-graph` when the file, the vanilla file or the glossary changed: the concept graph records their hashes.
3. `make test`: the Go tests, whose golden snapshots (`internal/core/testdata`) show every change to what the app derives from the file (armoury, auras, Tabletop Simulator
   lists, audit), and the Python tests of `tools/`. A change that moves a golden is reviewed and the golden regenerated as [testing.md](testing.md) says.

## Dependency direction and resolution order

References only point one way: **Battle Companies → vanilla and glossary**, and glossary terms may point to other glossary terms (`see`). Vanilla and the glossary never refer to the
Battle Companies file. A name the Battle Companies file does not define is looked up in vanilla, then in the glossary. The order is: a definition embedded in the entity that uses it,
then the Battle Companies file, then vanilla. Battle Companies wins: a rule with a vanilla name is its generalisation ("this Hero" for a named character) and carries `overrides`.
Vanilla scenarios and army bonuses are not used. Units are never redefined: a company's unit is a vanilla unit plus what the company changes.

A vanilla name defined twice is resolved by the loader to the **first occurrence**; `vanilla.pins` in the Battle Companies file names the few where another occurrence wins
(`{kind, name, occurrence}`; occurrences count the heroes list before the warriors list, case-insensitively). A pin whose occurrence does not exist is a warning ("vanilla drift").
The reviewed list and its notes are in `tools/data/duplicate_decisions.json`.

## The header and the identity of a ruleset

Every file the project authors (Battle Companies, glossary) starts with a top-level `name` and `version` (strings); the Battle Companies ones come from the rulebook's title page
("Stable Released Version 1.1" is `1.1`). The vanilla file is a third-party store, so it keeps `game` and `appVersion`. `core.RulesetMeta` reads them (and the marker that tells the kind of
file: `extends` for Battle Companies, `terms` for the glossary, `appVersion` for vanilla). A ruleset is identified by the content hash (SHA-256 of the compacted JSON, so whitespace does not
matter) of its three files: any change to any field is a new ruleset.

## The loader

`core.LoadRuleSet(vanilla, bc, glossary, log)` (`internal/core/audit.go`, `ruleset_v2.go`) merges the three files into the in-memory maps the engine queries:

1. Parse the vanilla file (`ParseVanillaWith`) and build the glossary (`BuildGlossary`).
2. Refuse a Battle Companies file of the old format (no `schemaVersion`, or 1) with the one issue that says so.
3. `lean.Decode`: the strict binder, `extends` and defaults, name resolution against the file, vanilla and the glossary, validation. Any error comes back as one `*RulesetReport`.
4. Re-parse vanilla with the duplicates the document pins (`LeanPins`) and apply its fill-ins (`ApplyLeanFillIns`: race, faction and unit type that vanilla leaves empty for a unit or mount).
5. `LeanBook` builds the whole rule set from the typed document; `LeanGlossaryExtras` adds the glossary terms the file implies (one per item, class rules, creatures, wanderers, consumables).

`RuleSet.Doc` carries the document. The readers, each in `internal/core`:

| Reader | Reads |
|---|---|
| `companies_lean.go` (`LeanCompanies`) | Company pages and profiles: charts, starting force, promotions, hero upgrades, own units (aliases), limits, officers, notes, oath |
| `gear_lean.go` | The armoury, annotations, item classes, abilities, creatures, wanderers, limits, fill-ins, unsold options |
| `paths_lean.go` | Paths: progression rows, limits, the path offers, starting actions and powers, characteristic limits |
| `rules_lean.go` | Rule texts, labels, targets (`LeanRuleTargets`), the aura table (`LeanAuraTable`), casting (`LeanCasting`) |
| `scenarios_lean.go` | Scenarios, scoring objectives, rewards, the selection tables |
| `campaign_lean.go`, `companyrules.go`, `recruitrules.go`, `aftermath.go`, `live_break.go` | The `campaign` parameters (below) |
| `tts_lean.go` | Tabletop Simulator figures ([tabletop-simulator.md](tabletop-simulator.md)) |
| `glossary_lean.go` | Glossary terms from the file |

**Maps, not database lookups.** The files are parsed once into immutable maps keyed by name, read concurrently without locks. **Shared by content**: campaigns with the same three hashes share
one set of maps; the cache is keyed by that triple and builds each set once, even under concurrent requests. The concept graph is computed into adjacency maps on first use per triple
(`core.Concepts`). **Uploaded rulesets** are stored once per hash, content-addressed, in the database; a campaign only references the hashes. The shipped files go through the same path.

## Normalisation: `extends`, defaults, names

`lean.Normalise` runs once after binding and is idempotent. `extends` (companies, units, items, paths): a child gets the base's value for every field it leaves at the zero value, except the
fields that stay its own (name, id, aka, definition, note, `tts` for items; faction, description, epigraph, notes and specialRules for companies); a list or an object the child writes replaces the
base's as a whole, and a child cannot override `true` with `false`. A loop of bases is an error. Defaults it fills: `id` (the slug of the name), a gear `gold` (the rating), a company's `faction`
(its name) and `maxModels` (`campaign.company.maxModels`), `ownPath.path` ("On Their Own Path"), a path's `kind` (`heroic`) and `dice` (`campaign.progression.hero.roll`), a scenario's and a
scoring objective's `side` (`both`), a rule target's `appliesTo` (`own`) and `match` (`any`), chart and start `count` (1).

**Names** compare with one function, `lean.NameKey` / `core.NameKey` (`internal/core/names.go`): lower case, accents dropped, apostrophes dropped, every other run of punctuation or spaces
one space (`Lothlorien` is `Lothlórien`, `Lake-Town` is `Lake Town`); plurals and "made" are not folded. Where the engine resolves a name:

| Name | Where | Rule |
|---|---|---|
| a name against another, or a map key | `sameName`, `NameKey` | `NameKey`; `aka` lists true synonyms; an `aka` that is a vanilla name of something else is refused |
| a company's own name for a unit | `CompanyProfile.AliasFor` | the company's own `units[]` entries with `extends` (label unique); a top-level `units[]` entry with `extends` is accepted by the checker but not read as an alias |
| the vanilla profile of a unit name | `RuleSet.ResolveUnit` | the company's own units (a unit on another, or a brand-new one), then the shared top-level `units[]`, then vanilla; a brand-new unit (`profile`, no `extends`) is registered as a vanilla-shaped profile when the book is built (`RegisterLeanUnits`) |
| a company by name | `BCBook.Company` | exact, else folded; `aka` |
| an item name against an item | `ItemKey`, `namesItem`, `SameItem` | gear identity only: plural s, "made", `&`, case, punctuation; the vanilla file's spellings need a bridge, the Battle Companies file writes exact names or `aka` |
| keyword spellings of the vanilla file | `keywordSpellings` | a fixed table in the vanilla bridge (the vanilla file is read-only) |

Two rule-name pairs that `NameKey` would conflate stay apart by distinct names or `overrides`: `Rapid Fire (Bolt Thrower)` / `Rapid-fire Bolt Thrower` and the vanilla `Swap with Me` / the Battle
Companies `Swap with Me!`. A rule written with its argument (`Terror (Beast)`, `Poisoned Attacks (X)`) resolves to the rule of its base name (`lean.BaseRuleName`).

## Derived, not stored

The app computes these from the data; the file does not carry them and does not need to:

- **Path offers and texts**: the path picker's summary and offers (`DerivePathOffers`) from the table, `heroicAction`, `spells`, `mastery` and `signature`; the text of a row that grants one rule (`RuleRowText`: `Name (Tag) - definition`) or only improves characteristics (`StatRowText`); `hidden` from the kind. A row keeps its `text` only where the words cannot be derived (a rule vanilla words otherwise, a mastery row with its "OR improve ..." alternative, a result with a ceiling or a second roll).
- **Item classes** from the vanilla type (`ClassesOfVanillaType`: mount, bow, armour, shield, banner, throwingWeapon, blowpipe, horn, spear, two-handed, upgrade); `gold` from the rating; `grantedTo: mount` of a mount that grants rules; a mount's stat block; `restrictions` (badges) from `who`; `pricedAs` items sold at their base's price.
- **Reserved options**: the options of vanilla units whose `availableIn` names only heroes (Lorien Guard, Hearthguard, Helmingas...) are never offered by a Choice of Options (`VanillaBook.ReservedOptions`); a company reaches one explicitly through a unit's `with`. The profile wargear no armoury sells (armour and hand weapons, natural weapons) is derived too (`ProfileWargearNotSold`): a model always starts with it, it is never an option or buyable.
- **Ids**, the keywords of a unit (`core.UnitKeywords`, [unit-keywords.md](unit-keywords.md)), the company rules sentence of `elvenWeaponry` (`ElvenWeaponrySentence`), the hero-upgrade rule text, the effective stats of a unit (below).

## Engine parameters

Every value the engine uses is a field of `lean.Campaign` (`campaign.go`) or of a few other sections, **required with a range**; there is no default in the code. A missing or out-of-range value is a load error naming
the path, in the upload report and at start-up. `lean.ParameterIDs` is the index from the ids of the engine parameters (A1, B3, C1...) to the paths. The values, ranges and meaning of each are in the
[tutorial](customizing-rulesets.md#11-engine-parameters). Where the engine reads them:

| Parameters | Reader |
|---|---|
| `campaign.company` (maxModels, leaders, sergeants, heroStart, equipmentSlots), `limits[]`, creature and wanderer counts, `paths[].limit` | `ParseCompanyRules` (`companyrules.go`) → `BCBook.Shape()`, `CompanyProfile.Leaders/Sergeants/HeroStart`, `CompanyUnit.BaseSlots`, the limit rules; a company's own `maxModels` must hold the officers |
| `campaign.recruitment` (die, adjust, rare), `campaign.company.startingInfluence`, `aftermathEffects[rendezvous\|vantagePoint].range` | `ParseRecruitRules` (`recruitrules.go`) → `BCBook.Recruiting()`; every chart is checked to cover `1..sides` once; the recruit window prints them (`RecruitInfo.Rules`) |
| `campaign.progression`, `campaign.experience`, `campaign.influence`, `campaign.injuries` | `ParseProgression`, `AftermathRules` (`aftermath.go`: `LevelEvery`, `Gains`, injury dice and rows, `NoPromotionBy`); `BCBook.ExperienceGain(key)` |
| `campaign.breakPoint` (default percent, comparison, courage test dice), a company's `breakPoint` | `BreakRules` (`live_break.go`) → `BreakConfig` for the live fold; the test is `casualties * 100` against `percent * startingModels` (never rounded) |
| `campaign.rating` | `RatingRules.Wargear`: the hero rating threshold; `BCBook.HeroBonus` is the profile bonus of a new hero |
| `campaign.scenarioSelection` | `LeanScenarios`; the ranges partition `1..sides` and each table lists `sides` scenarios |
| `campaign.characteristicLimits` | `LeanProgression`: `lowerIsBetter`, `peak` (and `willMaxOverrides`), `average`, `increases.courageIntelligenceTotalCap {value, includesGear}` |
| `magic.floor`, `magic.maxPerPower`, `magic.powers` | `LeanCasting` |
| `gear[].grantsSlots` | `Equipment.GrantsSlots`; `CompanyUnit.Slots()` adds them to `BaseSlots` (there is no Backpack name check) |

**Dice are data.** Every dice string is an `[N]dM` spec (N 1..10, M 2..100, `d66` refused), parsed once at load with `lean.ParseDice` (`core.DiceSpec`, `core.ParseDiceAt` names the key in the error) and rolled with
`core.Dice.Roll(spec)`. A table that does not cover the dice of its key is a load error naming the path (`core.CheckCovers`).

**Tables kept in the shipped shape.** `campaign.injuries` rows (with `effects`, persistence, retirement, `disables`, `grantsAtCount`, the treatments), `campaign.aftermathEffects`, `campaign.againstTheOdds`,
`campaign.matchInput`, `campaign.options` and `campaign.characteristicLimits` are read by the engine in the shape of the shipped file (`Rest` maps and `Free` values in the Go model): a custom file changes their numbers and
texts, copies their structure, and does not invent keys the engine does not know. `campaign.options[]` is the single list of switches (`key`, `scope` `rules` or `app`, `label`, `description`, `default`,
`implemented`, `swaps`); a reader that does not know a key ignores it and logs a warning. Objects that record a house-rule decision carry `confirmedByUser` and `defaultNotConfirmed` lists.

## How the engine applies what it reads

Behaviours worth knowing when you change the data (each is covered by tests; the code is the truth):

- **Item identity** is the name (`ItemKey` folds case, punctuation, the plural s and "made"): the same stats, class or price never make two items one. A wargear price group is one item per name with the price repeated.
  A warrior may buy an item only when it is exactly one of the items its profile options name (`OptionItems`, `GearMatchesOption`); a hero any item of its company's profiles. Chips and tooltips look the item up by its own name.
  A start, chart or promotion row that names one piece of a multi-item profile option ("Shield and Spear") gives the unit the whole option and prices it at the option's points (`completeBundle`).
- **Price rule**: a unit's points are the vanilla base profile cost plus the options it bought; only wargear no option has is charged its armoury rating (`OptionsCover`; the audit flag `price-mismatch` checks every row).
- **Effective stats** (`applyGearStats`, `gearstats.go`): armour by stage (best only), the best active shield `defenceBonus` (cancelled by a bow, crossbow, two-handed weapon or pike unless a rule lifts it: Expert Rider while mounted, Phalanx), and the plain `modifiesStats` of unit upgrades. **Conditional bonuses are item text, never added to the stats**: a `defenceBonus` or `attacksBonus` flagged `conditional` (Pavise, Small Shield, Elven Glaive) or a `statChanges[].condition` is a note. A shield's loss through the unit's own gear is a loadout condition and is computed. Disabled (injured) gear gives nothing.
- **Poison** is the special rule `Poisoned Attacks (<weapon>)` of a unit; wargear stays plain, except the Blowpipe, which grants it. *Envenom Weapon (X)* (`grantsForChosenWeapon`) is equipment bought with a chosen weapon of the unit's `PoisonableWeapons` (classes in `weaponClasses`); the choice is final, belongs to the weapon's name, and `BuyEquipmentFor` refuses a purchase without a valid weapon.
- **Limits**: every limit is read from `limits[]` (`id`, `classes` or a keyword, `maximumPercentage`, `roundUp`) and counts the model being recruited in numerator and denominator; a company's keyword limit always rounds up; a company's `limits.exempt` takes a unit or item out of both the count and the base; a model counts as Cavalry when its profile says so or it carries a mount.
- **Who** (`lean.Who.Admits`, the only reader) decides who may buy an item, take a hero upgrade, receive a granted rule, be a starting hero, or wear Elven-made weaponry; the refusal it returns is the text the armoury shows.
- **Officers**: a company has at most `leaders` Leaders and `sergeants` Sergeants; the rest are Heroes in the Making. A lost officer is replaced after the battle by a Sergeant (for a Leader), then another Hero; a Warrior is promoted to Hero only when no Hero is available (most Experience, ties by Rating then the controlling player) and gains Might, Will and Fate. A Hero promoted to fill a place stays a Hero. The Shire's Ranger replacement is the one case that displaces an officer ([frontend.md](frontend.md)). A unit On Its Own Path is never an officer.
- **Starting company** adds up to 105 (60 points of rating and gold plus 5 each for Might, Will and Fate of 3 heroes); the checker does not test it, `TestStartingCompanyPointsPlusGoldAre105InEveryCompany` does, with the documented exception of Defenders of the North (106: the book's list is 61 points at the current MESBG points). A start unit that is a hero by its profile must be one of the officers (`ValidateStart`).
- **Promotions**: the company's promotion applies only to the level-up roll; an officer chosen at creation, a Warrior taking a lost officer's place and a recruit that joins as a Hero (`heroes.recruitAsHero`) keep their profile and gain the Might, Will and Fate point of each. A unit the file marks `heroInTheMaking` starts as a Hero with its path to choose. A warrior promoting to another unit keeps only the gear the new profile lists.
- **Rare N**: at most N of the unit in the roster; injured units count, dead and promoted ones do not (`campaign.recruitment.rare`); a rare-exhausted result is recruited as a lower one. A lower result is a free choice of any lower result, allowed only when the rolled one cannot be recruited or a company rule says so (code, not data).
- **Paths**: `endOfPath` ("On Their Own Path") is assigned automatically to the units a company's `ownPath` names; with the option `customOnTheirOwnPath` those units start as Warriors and take the homebrew path on a roll of 6. Company Hero Upgrades may replace any rolled level-up result the hero does not already have.
- **Oaths**: a company's `oath.text` holds `{name}` exactly once, never at the start or end; `vow` is a button label of 1 to 40 characters; `campaign.company.oaths.{good,evil}` have the same shape and serve companies of a custom file that have none.
- **Scenarios**: a company's Victory Points are the sum of its objectives (`side` restricts to a role); the most points wins, equal is a draw. Rewards point at `campaign.aftermathEffects` entries, applied when their `condition` holds. `campaign.matchInput` describes what the players enter per match.
- **Auras and targets**: rings are matched to units by item, rule, power, Heroic Action or `hero` and merged per figure, kind, radius and tier; [aura-ranges.md](aura-ranges.md) is the spec. Rule targets (`target`, `bareTarget`) feed the unit cards' "Works against / Works for" ([unit-keywords.md](unit-keywords.md)). The curator's aura audit (what names a distance but draws no ring, and why) is `tools/data/aura_audit.json`.
- **Tabletop Simulator**: `unit.tts` and `gear.tts` are the fixed mappings to the mod's model names; the shape is checked by the Go validator and, when the gitignored `sources/tts/models.json` exists, `tools/lean_checks.tts_errors` checks every model against the mod's catalogue.

## The schema of the lean format

`definitions/battle_companies/battle_companies.schema.json` (JSON Schema 2020-12, `$defs` per model struct) describes the lean file. It is not used to check an upload (the decoder is the authority) but by the tools, the editors and the generated reference.

**The Go model is the contract and the schema is generated from it**: `internal/core/lean/model.go` and `campaign.go` carry the keys, types and tags (`required`, `enum`, `min`/`max`, `emin`/`emax`, `rest`), `schema_docs_test.go`
carries the description of every object and key, and `schema_gen_test.go` turns them into the schema by reflection. What a tag cannot say is written once in the generator: the polymorphic values (`Roll`, `DiceSpec`, `Rating`, `RuleRef`,
`AdvanceTo`, `Scalar`, next to their `BindJSON` in `types.go`), the `default` of each constant the defaults pass applies, and `schemaVersion` as `const 2`.

```
go test ./internal/core/lean -run TestSchemaUpToDate -update-schema    # after changing the model or a description: rewrites the schema file
make ruleset-reference                                                 # then rewrites docs/customizing-rulesets-reference.md from it
```

The tests fail when the pieces disagree: `TestSchemaUpToDate` (the committed file is byte-for-byte what the model generates), `TestSchemaMatchesModel` (a second, independent reading against the struct tags), `TestSchemaDefaults`
(each schema default is what `Normalise` writes), `TestSchemaFieldsAreDescribed` (every object and key has a description), `TestFixturesAgainstSchema` (every `testdata/valid/*.json` validates; for every invalid fixture the schema rejects, the decoder
reports something at that path or beneath it), and `tools/test_ruleset_reference.py` (the committed reference is what the generator makes). The schema is slightly stricter than the binder in two places: a `null` on an optional key
is accepted only where the model has a pointer to a scalar (`heroicAction`, `who.hero`), and a dice spec with leading zeros (`02d6`) is refused. `tools/validate_definitions.py` checks that the schema is valid and accepts the Go valid fixtures.

## Upload validation

An upload (the admin Rules files page, the campaign form's file pickers) is validated as a whole before anything is stored; every problem is collected and returned, none stops the report early.

1. `core.Rulesets.StoreAs` / `StoreAllAs` / `Check` run the same checks: kind, size (16 MB), the announced hash, well-formed JSON (a syntax error names its line and column), shape limits (1,000,000 values, 64 levels), the kind of document (`RulesetMeta`).
2. The Battle Companies file goes through the lean decoder (`lean.Decode`) against the vanilla file and glossary uploaded with it in the same request (the campaign form's picks, `CheckSet`, the online validator); what is not uploaded is the default (shipped) one, and a single-file upload (the admin page, the form with only that file) uses the defaults. A vanilla file or glossary that cannot be read is reported itself and the Battle Companies file is then checked against the shipped one with a warning. A file of the old format is refused with the one issue `schemaVersion 1 is not supported: ...`. Vanilla and glossary files are checked against their JSON schemas.
3. Any error: the whole list comes back as one `*core.RulesetReport` (wraps `ErrInvalidRuleset`; `Issues()` gives `RulesetIssue{File, Path, Message, Hint, Closest, Warn}`, `Truncated()` the count beyond 1,000); nothing is stored and no campaign is created. `StoreAllAs` checks every uploaded file before inserting any.
4. `CheckSet` (`Check` is its one-file form) is the dry run, behind the admin page's **Check this file** and the online validator at `/tools/validate` ([frontend.md](frontend.md#online-validator)): it takes the three contents (nil: not given), returns one report with the issues grouped by file (vanilla, glossary, Battle Companies) and never writes. At start-up the shipped Battle Companies file is checked against the shipped vanilla file and glossary, which are registered first (`RegisterDefaults`).

Report line, one per issue: `<file>: <json path>: <message>`, then `; closest: "<name>"` when a name did not resolve, then `  hint: <one line>`; a warning starts with `warn: ` and does not block. The order is the order of discovery and is deterministic.
The catalogue of messages is executable: `internal/core/lean/testdata/invalid/*.json` with the wording pinned in `*.want` ([testing.md](testing.md)). `make check-ruleset FILE=... [VANILLA=... GLOSSARY=...]` prints the report and exits 1 on errors, 2 when it could not run.

## The golden snapshot

`go test ./internal/core -run Snapshot` compares everything the app derives from the Battle Companies file (all 37 companies: charts, armoury, profiles, progression, campaign tables, glossary extras) with `internal/core/testdata/snapshot/`; `auras_golden.txt` and
`tts_golden.txt` do the same for the aura rings and the Tabletop Simulator lists. A golden that changes in a refactor means the refactor changed behaviour; a deliberate data or engine change updates it (`-update-snapshot`, `-update-auras`) after the diff is reviewed ([testing.md](testing.md)).
`TestCustomRuleset*` rows change one engine parameter in a copy of the shipped file and check the effect through the built `RuleSet`, so nothing stays hard-coded; `cmd/rulecheck/examples_test.go` runs the guide's examples.

## Audit report

`make audit` (`go run ./cmd/server audit [--out DIR]`, default `tmp/audit/`, gitignored, no database) loads the shipped rules and writes one markdown file per Battle Company plus `index.md`. The data comes from the real code (`BuildDetail`, the recruit charts, `BCBook.Armoury`, the armoury's `whyNot` for a
warrior and a hero of every distinct profile, `GearMatchesOption`, the tooltip text `equipmentFor` shows); the output is stable, so two runs can be diffed (`internal/core/audit.go`, `audit_render.go`). The index counts anomalies per kind and company: `offer-not-derivable`, `option-unbuyable`, `price-missing`, `unit-unresolved`, `unit-no-wargear`,
`duplicate-name`, `tooltip-name`, `tooltip-missing`, `option-unknown-item`, `name-format`, `rule-unresolved`, `price-mismatch`, `partial-bundle`. Flags are leads for a reviewer, not verdicts.

## Reference tables (`reference` in the glossary file)

Besides `terms`, the glossary file carries structured rulebook tables the terms only describe (`tools/glossary_reference.py`, hand-transcribed; the validator and `tools/test_to_wound.py` check them). `reference.toWound` is the To Wound Chart (rulebook page 44):
`strengths` and `defences` 1..10, `cells[s-1][d-1]` the roll for Strength `s` against Defence `d` (`3+`..`6+`, `6+/4+`, `6+/5+`, `6+/6+`, `-`), `notation`, `notes`. The validator requires the complete grid, only those values, and monotonicity (never easier as Defence rises, never harder as Strength rises).

## The concept graph file

`definitions/concepts/concept_graph.json` (schema `concept_graph.schema.json`) is built by `tools/build_concept_graph.py` from the shipped triple and holds only what cannot be recomputed from the text: `builtFrom` (the three ruleset hashes, as `core.RulesetHash`
computes them), `nodes` (the glossary terms exactly as the app builds them, via `go run ./tools/conceptnodes`), `edges` (`grants`, `cancels`, `lifts`, `requires`, with `via`) and `ambiguous`. Edges are derived from the lean file (item `grants`, path heroic actions and rule rows, shield `defenceBonus` cancellations and lifts,
`requiresMount`, `who`) plus the reviewed `tools/concepts_curated.json`. `make validate` fails on a stale graph; `make concept-graph` rebuilds and validates. Design and consumers: [concept-graph.md](concept-graph.md); details of the checks: [tools/README.md](../tools/README.md).
