# Battle Companies JSON: curator's audit for a leaner format

Read-only audit of `definitions/battle_companies/battle_companies.json` (920 KB pretty, 609 KB compact; schema 94 KB;
generated by `tools/build_battle_companies.py` and `tools/bc/*.py`, about 4,600 lines of Python in `tools/bc/`).
Goal: a lean format where people add their own companies, units, equipment and paths, with no loss of feature or
content. Sizes below are compact JSON bytes.

## 1. Summary

- **Real content is small.** The rules a person authors (companies' tables, paths, equipment, unique wargear) are
  roughly 150 KB. The rest is: rulebook prose displayed verbatim (about 320 KB of strings of 80+ characters), curator
  metadata (`reason`, `note`, `evidence`, `source`, `status`: 56 KB, 9 percent), derived or duplicated data, and reviewed-case
  tables that are one simple rule in disguise.
- **Biggest wins, in order:** (1) scenario scoring stored three times (about 60 KB); (2) `data.auras`, `data.ttsModels`
  and `data.gearAnnotations` are mostly derived or curator working data (about 120 KB, can move to separate optional
  files); (3) the "option is not sold" family (`optionSales`, `reservedOptions`, `profileWargearNotSold`, `wargearReadAs`,
  `unitFillIns`, `mountFillIns`: 31 KB) collapses to about 6 KB of rules plus a handful of exceptions; (4) company `effects[]`
  repeats typed fields already on the company (about 15 KB of 19.6 KB); (5) `vanillaAmbiguities` (22 KB) leaves the BC file;
  (6) `magicalPowers` copies 43 vanilla definitions (13 KB) that equal vanilla text.
- **Rough total saving without losing a feature:** 200 to 250 KB compact (35 to 40 percent), more if prose moves out.
- **Go side:** 17 Go files each decode their own partial struct of this one file (see section 6). A single typed
  loader would remove most of the "cope with the shape" code.

## 3. Findings

For each: what is wrong, the leaner shape, the saving and the risk.

### 3.1 Scenarios: the scoring text exists three times

`scenarioScoring[]` (21 KB: `{name, points[[ {text, points} ]]}`), `scenarioDetails[].scoring` (prose, 17 KB) and
`scenarioDetails[].scoringObjectives[]` (44 KB) all hold the same sentences. In `scoringObjectives` the sentence is
stored in `text` and again inside `options[].text` (see `objectiveMarkers` in Seize Ground: the whole tier text twice).
Unique text is about 17 KB. Go reads `scenarioScoring[].points[].text` (options.go) and `scoringObjectives`
(the same file, for the typed form).

- Leaner: one `scenarios[]` list (replacing `scenarios`, `scenarioScoring`, `scenarioDetails`), each with `name`, `description`,
  `outline`, `armies`, `layout`, `startingPositions`, `objectives`, `specialRules`, `roles`, `rewards`, and `scoring[]`
  as typed objectives where each tier text appears once (`options[{text, points}]`; drop the objective-level `text` when it
  is just the joined options; `scoring` prose is then unnecessary).
- Saving: about 60 to 65 KB (scenarioScoring 21 KB, scoring prose 17 KB, duplicated option text about 20 KB, `scenarios`).
- Risk: low if the typed objectives are verified to cover every `scoring` bullet (the generator zips them "same order");
  the validator should assert that the count matches. Keep `side`, `secret`, `instruction`.
- Also: `data.scenarioDetails` is 76 KB of rulebook prose. See section 5.

### 3.2 `vanillaAmbiguities` (22 KB, 91 entries)

Statuses: 64 `equivalent`, 22 `firstWins` (with an `occurrence` index recorded), 2 `overridden`, 3 `pinned`. Go
(`duplicates.go`) only needs to know which occurrence wins; everything except the 3 pinned is "the first" and is an audit
record (notes are 14.7 KB).

- Leaner: the BC file keeps only the genuine exceptions, `vanilla.pins: [{kind, name, occurrence}]` (3 entries).
  The review record (status plus note) moves to a curator-side file (`tools/duplicate_decisions.json`, not shipped) which the
  validator still checks, so the decision is never asked twice.
- Saving: about 20 KB.
- Risk: the decision record is lost for users who only have the JSON; acceptable since a user-authored file never has these.
  Go side: `ParseVanillaAmbiguities` and the `audit.go` consumer need a pins-only shape (see questions).
- Better still: fix the duplicates in the Go loader with the rule "first wins unless pinned" and delete the reviewed list from the shipped file.

### 3.3 The "option sales" family is one rule plus exceptions (31 KB to about 6 KB)

- `optionSales` (22.7 KB, 68 items): 62 are `notSold` for "a banner, war horn or war drum" (same 178-character `reason` and
  same `source` repeated 62 times: 14.8 KB of the section is reason plus source). That is one rule: *any vanilla option whose
  gear is a banner, war horn or war drum is not sold (the Company Standard, Horn and Drum replace it)*. The other 6 are real
  exceptions: 3 `granted` (e.g. Ranger of the North + Armour comes only from the starting company), 1 `readAs` (Cave Troll
  Hand-and-a-half hammer = Hand-and-a-half Weapon), 1 `ownItem` (Troll Spear), 1 other.
  Leaner: `rules.notSoldOptionTypes: ["banner","horn","drum"]` (matched on vanilla option gear type) plus `optionExceptions[]`
  with 6 entries. Saving about 19 KB.
- `reservedOptions` (1.6 KB, 10): options restricted in vanilla to named heroes' army lists (`availableIn` only heroes). This is
  derivable from vanilla (`availableIn` lists only hero names) and is a rule, not a table. Saving 1.6 KB. Risk: the derivation
  must reproduce the same 10 (the generator already computes it; keep that as a validator check).
- `profileWargearNotSold` (5 KB, 23 items, e.g. `Armour` with 40 unit names): "wargear in the vanilla profile that no Armoury item sells"
  is fully derivable from vanilla plus `wargear/equipment`. It is stored only to avoid computing it. Leaner: remove, compute in
  the loader (or at start-up, with a golden test). Saving 5 KB.
- `wargearReadAs` (1.1 KB, 6): "bow with poison arrows" read as "Bow" because the unit has Poisoned Attacks (Bow). It is read
  by the generator and the validator only (no Go reader). It is a transcription alias for the company-list parser, so it
  belongs in `tools/bc/core.py` (a build input), not in the shipped JSON. Saving 1.1 KB.
- `unitFillIns` (2 units) and `mountFillIns` (5 mounts) (2.9 KB): a vanilla gap patch (race/faction/unit type missing in vanilla).
  Both are a reasoned patch of a third-party file. Leaner: one `vanillaPatches` object `{units: {name: {race, faction, unitType, baseSize}}, mounts: {...}}`
  without `reason`/`source` (move them to the curator file). Saving 1.5 KB; risk: none, but the `REVIEW:` status needs a home (curator side).
- Together: about 28 KB saved. Risk: the Go code that uses `OptionSales`, `ReservedOptions`, `ProfileWargearNotSold`,
  `UnitFillIns` (battlecompanies.go, audit.go, rules.go, ttsnames.go, world_aura.go) must switch to the rule form; see questions.

### 3.4 `gearAnnotations` (61.7 KB, 106 items) overlaps `wargear`, `equipment` and unique wargear

- 54 of the 106 annotated names are also items of `data.wargear` / `data.equipment` / `companies[].uniqueWargear`
  (32 + 25 + 5 entries). For 26 of them the annotation's `definition` is byte-identical to the item's own `definition` (6.4 KB). The rest
  (52) are vanilla wargear and unit options that have no BC row.
- `evidence` (6.8 KB) and `status` (curated/derived, 71 vs 35, 1 KB) are curator working data, never read by Go (not in the Go struct).
- 35 entries are `derived` (e.g. `Armour` + `statChanges`), the others `curated`. Many entries only say `classes: ["bow"]` because the
  vanilla type already says so (`evidence: "vanilla type: bow"`, 9 times; `vanilla type: mount`, 9; `vanilla type: armour`, 2).
- The weapon/armour class texts (`modifiers`, 1.9 KB) and `abilities` keys are a closed vocabulary; fine.
- Leaner: merge the annotation fields (`classes`, `grants`, `abilities`, `statChanges`, `ranged`, `aliases`) into the item that owns them
  (`wargear.items[]`, `equipment.items[]`, `uniqueWargear[]`); keep a smaller `gear[]` only for vanilla gear that BC does not sell.
  Drop derived entries (a class that equals the vanilla `type` needs no annotation): apply "class = vanilla type" as the default and
  keep only the 71 curated ones. Drop `evidence`/`status`.
  Resulting shape: one list `gear[]` with `{name, source: bc|vanilla, classes?, grants?, abilities?, ...}` where an item that people
  add themselves is one object (price, text, class, rule) in a single place. Saving: about 6.4 KB (duplicate definitions) + 7.8 KB
  (evidence/status) + about 10 KB (derived entries and repeated keys) = about 24 KB.
- Risk: medium. The tooltip text rule ("definition is the source text plus the class rule text") must be preserved; a missing
  `definition` has to be computed the same way by the loader. `gearidentity.go`, `poison.go`, `glossary_extras.go`, `gear.go` read it.
  This is the open bead `a2g` (gear annotations), so coordinate: do not restructure while the reviewer pass is open.

### 3.5 `data.auras` (34 KB) is mostly derived or documentation

Parts: `entries` 21.5 KB (52 entries), `excluded` 5.2 KB (26), `unreachable` 4.1 KB (181 names), `kinds` 0.7, `groups` 1, `outOfScope` 0.5, `text` 0.8.
`excluded`, `unreachable` and `outOfScope` (9.9 KB) are records of what is NOT an aura and of rules whose names no unit reaches; they exist
for audit (`tools/test_auras.py`), not to drive the app. `entries[].reason` (6.5 KB) is curator provenance. Each entry restates
`tip` text, which duplicates the rule definition elsewhere (Banner, Stand Fast): the `tip` is a shortened copy of rulebook text.

- Leaner: ship `kinds`, `groups` and `entries` without `reason`; move `excluded`, `unreachable`, `outOfScope`, `reason` to the curator tooling;
  derive `tip` from the glossary or rule definition (or keep it where it is deliberately shorter, flagged).
  Saving about 16 KB (`excluded` + `unreachable` + `outOfScope` 9.9 KB, `reason` 6.5 KB). Risk: low; the app ignores them
  (to confirm in `auras.go`).
- Overlap with `ruleTargets` and `parameterisedRules`: all three say "this rule affects X" in different vocabularies: `ruleTargets.names`
  (53 rule names to `appliesTo`/`target`), `auras.entries` (radius, who is affected) and `parameterisedRules` (what X is). They are
  consumed by different features (`company.go` list targets; the TTS rings; the popup) so a full merge is risky, but a common
  `rules[]` record `{name, parameter?, target?, aura?}` keyed by the keyword name is feasible: one object per rule, where each facet is optional.
  Saving about 3 KB of repeated names plus one place to edit; risk: medium (three Go readers).

### 3.6 `data.ttsModels` (4.9 KB)

Mapping of units to the Tabletop Simulator mod's figures (`standIns`, `mounts`, `riders` 18, `names`, `defaultOptions`, `markerOptions`). It is
integration data for one external mod, unrelated to rules; extracted by `tools/extract_tts_models.py`. `reason` strings are 1.4 KB.
Leaner: move to its own file `definitions/tts/ttsModels.json` (optional, versioned apart from the rules) so rules-only forks and
user-authored rulesets need not carry it. Saving 4.9 KB from the BC file, zero loss. Risk: low; the Go loader needs a second optional file.
User-added units then need a TTS mapping only if they use the mod.

### 3.7 `data.magicalPowers` (18.8 KB)

All 43 items are vanilla powers, the `definition` equal to vanilla text in 43 of 43 cases. What BC adds is `learnable`, `range` and `casting`
for 31 powers on the Sorcerer's list, plus `castingRule`. Leaner: `magic.castingRule` and `magic.powers: {name: {range, casting}}` (31 entries,
about 2 KB) with the definition looked up in vanilla. Saving about 13 KB, risk: low (the validator can assert equality with vanilla at build
time; the vanilla file is never edited). Check the 12 non-learnable powers, which need `learnable: false` only.

### 3.8 `keywords`, `parameterisedRules`, `ruleTargets`, `minorSpecialRules`

- `data.keywords` (106 rules, 31.5 KB): 28+21 with `tag` (Active/Passive), 32 `overrides` vanilla. 56 have a `source` of the form
  `Path of the X`. Their definitions (10.9 KB) are also embedded in the progression row text of the paths: in 55 progression rows the `text`
  contains the whole keyword definition (10.7 KB duplicate). Leaner: the row stores the rule name only; `text` is derived
  (`"{name} ({tag}) - {definition}"`). Saving about 10.7 KB. Risk: low (check that every row's text equals that composition; if not, that row
  keeps an explicit `text`).
- `parameterisedRules` (6.7 KB, 7): `definition` is copied from vanilla through `definitionFrom` (4.2 KB prose). Keep `name`, `pattern`, `parameter`,
  and `definitionFrom`; the loader resolves the text. Saving about 4 KB.
- `ruleTargets` (8.2 KB): `patterns[]` list `variants` (21 spellings of the same rule, 1 KB) which the loader can derive by matching `pattern`; the
  `names[]` (53) have `appliesTo/keywords/keywordMatch/target`. These facts belong on the rule itself (`keywords[].target`), see 3.5. Saving about 2 KB
  (variants and keys) plus fewer places to edit.
- `minorSpecialRules` (14 items of `{specialRule}` plus a few with `parameterKind`): a list of rule names that qualify as "minor". It is a flag on the
  rule: `keywords[].minor: true`. Saving 0.6 KB, one section less.
- `limits` (3 entries, 391 B) and `campaign.company.maxModels` belong together.

### 3.9 `data.paths` (53 KB, 13 paths)

- `progression` is 32.8 KB (of which about 10.7 KB is keyword text duplicated, see 3.8).
- `offers` (6.8 KB) is **derived** from the table by the generator (documented as "derived from the table for the path picker's tooltip"), including a
  ready-made English `summary` sentence. The Go side needs `offers` only for the tooltip; computing it at load is a pure function of `progression`.
  Remove from the data (saving 6.8 KB), compute in Go (or ship it only as a build artefact). Risk: the summary phrasing is generator code; moving it
  to Go means two code bases to keep in step.
- `startingHeroicAction` (4.2 KB) holds the heroic action's `{name, definition}`; the definition is already in `keywords` or the glossary (vanilla
  spells "Heroic Channeling/Channelling"). Reference by name. Saving about 3.5 KB.
- `spellList` (1.8 KB) overlaps `magicalPowers` (the 31 powers with `casting`). The path's list can be `magic.powers` filtered by `path`.
- `description` (1.2 KB), `startingNote` and `diceNote` are prose; fine.
- Quirks: `kind` (heroic/custom/endOfPath) plus separate booleans `canLevelUp`, `givesExperience`, `countsAsHero`, `staysWarrior`, `homebrew`,
  `startsOnPathWhenRecruited`, `selectable`, `assignedAutomatically`, `assignedWhen`, `enabledBy`, `limitPerCompany`, `implemented` (about 20 keys
  across the paths, most only on the 2 non-heroic paths) are a closed set that really encodes 3 path kinds. A `kind` with defaults per kind
  would remove the booleans (about 0.5 KB, mainly clarity for a person adding a path).
- A person adding a path today must write: a path object, its `progression` rows (2d6, each with a `text` and typed `options`), `maximums`, new rules in
  `keywords` with `source: "Path of ..."`, minor rules, possibly a Heroic Action; and the `offers`/`summary` are generated, so a hand-added path in the
  JSON has no tooltip (a clean-break format would compute it in the loader; this is the strongest argument for removing `offers`).

## 4. Companies (139 KB): what a person must touch today

Per-company: `description` 31 KB (772 B each; flavour prose), `effects` 19.6 KB, `reinforcements` 16.6 KB, `startingCompany` 9.5 KB, `oath` 8.5 KB
(invented flavour text, not in the rulebook: confirm; the `vow` is unique per company), `heroUpgrades` 8.4 KB, `notes` 6.6 KB, `specialChart` 6.3 KB,
`advancements` 6.2 KB, `unitAliases` 4.2 KB, `uniqueWargear` 3.9 KB, `specialRules` 2.5 KB, `rareUnits` 2.3 KB, `ruleSubstitutions` 2 KB, etc. 28 distinct keys, 9 of
which appear in all 37.

To add a company today a person must write, at minimum: `name, alignment, description, startingCompany, reinforcements, heroUpgrades, oath, effects`
(all required), then every optional key the company needs, and add each hero upgrade's rule to `data.keywords` (all 44 heroUpgrade names exist in
`keywords`), and a unit that vanilla lacks needs a delta (`addSpecialRules`/`addKeywords`) written twice (in `unitAliases` and again in `effects[unitAlias]`).

Redundancies inside a company:

| Duplicate | Evidence | Saving | Risk |
|---|---|---|---|
| `effects[kind=heroUpgrade]` (44, 4.8 KB) repeats `heroUpgrades[]` (name + specialRule) | every heroUpgrade effect has the same `name`/`specialRule` | 4.8 KB | low |
| `effects[kind=onTheirOwnPath]` (17, 3.2 KB) repeats `onTheirOwnPath` + `onTheirOwnPathRulebook` (468 + 429 B) | the same names in all 17 companies | 3.2 KB | low; `onTheirOwnPathRulebook` is a second spelling kept for audit |
| `effects[kind=unitAlias]` (9, 3.2 KB) repeats `unitAliases[]` (4.2 KB) in 7 companies | counts per company match (1/1, 2/2) | 3.2 KB | low |
| `effects[kind=ruleSubstitution]` (7, 2.3 KB) repeats `ruleSubstitutions` (2 KB) | same sentences, with `text` | 2.3 KB | low |
| `effects[kind=maxModels]` (15, 0.8 KB) repeats `maxModels` (30 B each) | | 0.8 KB | none |
| `effects[kind=uniqueWargear|limitExemption|limitOverride|grantedRule|specialUnit|breakPoint|...]` repeat the typed top-level fields | `limitExemption` 4, `limitOverride` 3, `grantedRule` 3, `specialUnit` 3 | 2 KB | low |
| `rareUnits` (18, 2.3 KB) repeats the `rare` count that sits on `specialChart`/`reinforcements` result rows (`rare: n`) and the roll | `rareUnits` has `where: "specialChart", roll: [4,6]` | 2.3 KB | low: derive from the table |
| `vanillaFaction` (18) equals `name` in 18 of 18 | `vanillaFaction == name` | 0.3 KB | none: make it optional only when different |

| `unitAliases` entries of the "printed name = base unit + `selectedOptions`" kind | see 4 table in docs | small | n/a |

Taken together `effects[]` can shrink from 19.6 KB to about 4 KB: keep only the effects with no typed twin (`heroPromotion`, `recruitFallback`,
`startingHeroRestriction`, `compositeModel`, `aura`, `raceBalance`, `includedUnitPoints`, `modelCount`, `unitTypes`, `companyLimit`, `rangerReplacement`,
`reinforcementReplacement`, `recruitAsHero`). Note the `layer` key (management / match / both) which is repeated on every effect (112 B per company).
Better: effects as the only form (`effects[]` with typed kinds), and `heroUpgrades`, `unitAliases` etc. generated from effects by the loader, or
the other way round. One representation is enough; the owner should pick it (recommendation: **effects only**, since it is the extensible vocabulary,
`kind` documented in `tools/bc/company_effects.py`; or typed fields only for the simplest cases and effects for the unusual).
Risk: Go reads both forms today (`companyprofile.go` has fields for `heroUpgrades`, `ruleSubstitutions`, `unitAliases`, `onTheirOwnPath` AND `effects`); the
Go side must say which it prefers.

Per-company overrides: companies override the 33.33 percent bow limit (`limitOverrides` 3, `effects[limitOverride]`), the Break Point (Muster of Isengard 66 percent:
`breakPointPercentage` plus effect), `maxModels` (15), `companyLimits` (1). All are simple scalars; fine once the duplicate effect form is gone. No
unit is redefined: `UNIT_DELTAS` gives 2 deltas (Ranger of Ithilien, Goblin Hulk) as `unitAlias` with `addSpecialRules` / `addKeywords`. `LEGACY_NAMES`
is empty. So "per-company overrides that base-unit + delta would cover" is already the case; nothing to cut there.

Prose: `description` 31 KB and `oath` 8.5 KB are flavour; `notes` and `specialRules` are rule sentences "exactly as printed".

## 5. Rulebook prose in the committed JSON (copyright)

Strings of 80+ characters total 323 KB, i.e. over half of the compact file. The repo is public and `sources/` is gitignored, yet the JSON contains the
Battle Companies document's prose (a free community document, but the owner treats it as protected):

| Section | Bytes of long strings |
|---|---|
| `data.scenarioDetails` | 75.7 KB (objectives, scoring, special rules, layout, descriptions) |
| `data.companies` | 58.5 KB (description 31 KB, notes, special rules, rule sentences in effects) |
| `data.gearAnnotations` | 35 KB (item definitions, partly from vanilla) |
| `data.paths` | 24 KB (progression row text, description) |
| `data.keywords` | 21.4 KB (rule definitions: path rules, company rules) |
| `scenarioScoring` | 15.2 KB (duplicate of scenarioDetails) |
| `data.magicalPowers` | 14 KB (vanilla text) |
| `data.vanillaAmbiguities` | 13.9 KB (curator notes) |
| `data.optionSales` | 13 KB (curator reasons) |
| `data.auras` | 8.4 KB |
| `data.equipment` | 4.7 KB |
| `campaign.*` combined | about 24 KB (injuries 3.5, scenarioSelection 3.5, breakPoint 2.6, ...) |

Some of it is display text that the app must show (rules are shown next to units, matches happen offline), so removing it removes features. Options for the
owner: (a) accept it (the document is a free community release and the credit block names the authors); (b) load display prose from a second optional file that the user
generates locally from the document (`rules_text.json`, not committed), leaving ids and typed data in the committed file. (b) fits the "add your own companies"
goal too (a user's text lives in the user's file) but is a bigger change, and breaks a clean checkout without the extraction step. **Owner decision needed.** Whichever is
chosen, duplicate prose (3.1, 3.8, section 4) goes first since it removes bytes with no feature loss.

## 6. What the Go side does to cope with the shape (questions for the backend planner)

At least 17 Go files decode a private partial struct of the same document: battlecompanies.go, companybuild.go, ruleset.go, duplicates.go,
progression.go, options.go, vanilla.go, creatures.go, ato.go, glossary_extras.go, aftermath.go, ttsmodels.go, towound.go, injuries.go, glossary.go,
auras.go, companyprofile.go, plus cmd/server/world_settings.go. A single typed `BattleCompaniesRules` struct would turn the shape into one place.

Questions:

## 7. Quirks in the schema and the file

- Schema is `additionalProperties: false` almost everywhere (27 times) but 71 `enum`s mirror Python tables (`ABILITY_KEYS`, effect kinds, gear classes): every new
  kind is a change to Python, schema and Go. For user extensibility, kinds an engine does not know should be tolerated (warn) rather than invalid.
- Many numbers appear as `{warrior, hero}` pairs even for equipment that costs the same for both; and `rating` equals `gold`.
- Section naming is mixed: `data.wargear.items[].names[]` (list of aliases, 3 aliases for one entry, e.g. "Armoured Horse", "Goat", "Galadhrim Steed")
  versus `name` elsewhere; `data.companies[].reinforcements.table[].result.type` with `unit`, `nothing`, `choice` booleans; `specialChart` separate from
  `reinforcements` though both are D6 tables.
- Status keywords in different places: `status` (`equivalent`/`notSold`/`curated`/`derived`), `inferred`, `undecided`, `implemented`, `REVIEW:` prefix in notes:
  one `provenance` convention (`confirmed | inferred | review`) would be easier to validate and filter.
- `campaign.*` mixes engine parameters (costs, thresholds) with display prose (`text`) in the same object. Splitting `text` out would make the numbers easy to override
  but loses the single place per rule; keep as is, only strip prose that has no reader.
- Pretty-printed with 920 KB versus 609 KB compact (34 percent is whitespace). Shipping compact or indent 1 is a free saving but hurts diffs; the generator can
  write compact and the repository can keep a pretty copy only for review.
- `credit` is a list of one; `extends` is a string with a descriptive name, not an id.

## 8. Proposed target layout (sketch)

```text
definitions/
  battle_companies/
    rules.json                 # engine parameters + catalogue, schemaVersion 3, hand-editable
    scenarios.json             # one list: name, description, setup, typed scoring (each text once), rewards
  companies/                   # user-extensible: one file per company (or a "companies": [] in a user file)
    arnor.json                 # {name, alignment, description, vanillaFaction?, oath, start, reinforcements, special?,
                               #  advancements, heroUpgrade(s), unique wargear, effects[] (only what has no typed field)}
  extensions/                  # optional, user-authored, merged by id (units, items, paths, rules)
  tts/ttsModels.json           # optional integration data
  vanilla/ glossary/ concepts/ # unchanged
```

`rules.json` (target keys):

```text
{ schemaVersion, name, version, extends, credit,
  campaign: { company, experience, injuries, progression, characteristicLimits, influence, rating,
              againstTheOdds, scenarioSelection, gold, aftermathEffects, breakPoint, options },   # prose only where read
  limits[], validations[],
  rules[]:      { name, definition, source, tag?, overrides?, minor?, target?, parameter?, aura? },  # merges keywords,
                                                  # minorSpecialRules, parameterisedRules, ruleTargets, aura facets
  magic:        { castingRule, powers: { name: {range, casting} } },        # definitions from vanilla
  gear[]:       { name, kind: wargear|equipment|unique|creature|wanderer, price: {influence, rating},
                  classes?, grants?, abilities?, statChanges?, definition?, ... },   # merges wargear, equipment,
                                                  # gearAnnotations, unique wargear
  paths[]:      { name, kind, maximums, progression[{roll, options[]}] },    # offers/summary computed
  vanilla:      { pins[], gaps{units,mounts}, notSoldOptionTypes[], optionExceptions[] }
}
```

Curator-only (not shipped): `reason`, `note`, `evidence`, `status`, `excluded`, `unreachable`, `outOfScope`, review record of duplicates,
`wargearReadAs`, TTS provenance. Kept in `tools/` as data files read by the generator and the validator.

Adding something in the target: a company = one file; a unit = a vanilla name plus `selectedOptions`/delta (no change); an item = one `gear[]` object; a path
= one `paths[]` object whose rules are `rules[]` objects; no second place to edit.
